## 一、版本目标

在已有分层产品结构（免费 / 会员 / 点券）基础上，完成以下商业化补强：

1. **推演点券扩档**：新增 ×3、×10 批量套餐（UI 已有结构，更新数据）
2. **追问次数封顶**：统一为 66次/本卦（付费用户），消灭滥用漏洞
3. **专业解读月度配额化**：月会员 66次/月，年会员 88次/月
4. **年度会员权益统一**：年费 ¥88/年，专业解读 88次/月
5. **iCloud/CloudKit 次数同步**：点券前置技术保障，解决换机丢余额问题
6. **付费触发时机重构**：问题页、结果页植入引导，大师/推演/追问有独立拦截提示
7. **大师点券余额展示**：在「我的」页面 + 摇卦结果页解读模式选择处双点位展示

## 二、六个问题的决策结论

### 2.1 要不要出推演 3次 / 10次套餐？

**结论：出，两个档都出。**

单次 ¥8 解决冲动需求，但重度用户（咨询感情/事业多个问题）会频繁支付，体验差且客单低。

| SKU | 价格 | 单次均价 | 节省 | App Store 档位 |
|-----|------|---------|------|--------------|
| 推演 ×1 | ¥8 | ¥8 | — | ✅ 标准档 |
| 推演 ×3 | **¥18** | ¥6 | ¥6 | ✅ 标准档（UI 当前假数据¥28需更新） |
| 推演 ×10 | **¥45** | ¥4.5 | ¥35 | ✅ 标准档（UI 当前假数据¥68需更新） |

> ⚠️ **UI 文案说明**：图五推演购买页当前显示 ×3=¥28（约9.3/次）、×10=¥68（约6.3/次），均为假数据且定价不合理（¥28/3≈9.3元，比单次¥8还贵）。正式上线前需将数字改为 ¥18（约6/次）和 ¥45（约4.5/次）。

**定价逻辑**：
- 推演×3 ¥18：低于大师×3 ¥28，体现推演是大师的"配套"而非主角
- 推演×10 ¥45：对标重度用户的季度用量，比大师×10 ¥68 更亲民，鼓励推演作为常规工具使用
- 决策套餐（大师×1 + 推演×1）¥18：与推演×3 同价，形成"本次用完整套餐 vs 存3次推演额度"的自然对比

**注意**：×3 和 ×10 上架前，**必须先完成 iCloud/CloudKit 同步**（见 §2.5），否则换机会导致余额丢失。

### 2.2 追问次数要不要改？

**结论：改，统一封顶为 66次/本卦（全体付费用户），免费保持 3轮。**

「无限」的问题：少数用户把追问当免费 AI 聊天，一卦追问数百次；并且 AI 结果页的购买卡片（图一）已经显示「购买后可享「66次」追问」，66次即为既定 UI 数字，直接沿用。

真实用量：核心用户一卦问超过 10 个问题已是极限，66次 是安全天花板。

| 用户层级 | 追问上限（本卦内） |
|---------|---------------|
| 免费用户 | **3轮** |
| 月会员 | **66次** |
| 年会员 | **66次** |
| 大师点券用户（已购本卦） | **66次** |
| 推演点券（本卦） | 跟随当前解读层级 |

> 说明：月会员与年会员追问上限统一 66次，不做区分。追问的差异化体现在专业解读次数（月66 vs 年88），不体现在追问次数上，逻辑更清晰。

### 2.3 会员无限专业解读要不要限？

**结论：要限，月会员 66次/月，年会员 88次/月，制造明显升级差异。**

| 用户层级 | 专业解读配额 |
|---------|-----------|
| 免费用户 | 每日 1次 |
| 月会员（¥9.9/月） | **66次/月**（≈每天2次） |
| 年会员（¥88/年） | **88次/月**（≈每天近3次） |

**文案方向**：
- 月会员卡片文案：「每月 66次专业解读」（替换现有「无限专业解读」）
- 年会员卡片文案：「每月 88次专业解读」
- 对比年月差异：年会员多 **34%** 解读配额，叠加大师赠送数量差异，年费吸引力显著

> ⚠️ **UI 文案说明**：图三升级专业版页面当前显示「无限专业解读」「无限提问」，为假数据，需更新为对应数字。

### 2.5 上点券之前做 iCloud / CloudKit 同步次数

**结论：必做，是上线 ×3 / ×10 点券的 P0 前置条件。**

点券（Consumable IAP）苹果不支持恢复购买。若次数只存本地：用户删 App 或换机，余额归零 → 投诉退款。

**技术方案（CloudKit Public/Private Database）**：

```
Record Type: UserQuota
  - appleUserID: String（从 iCloud 取，无需 Sign in with Apple）
  - masterCredits: Int（大师点券余额）
  - deductionCredits: Int（推演点券余额）
  - monthlyReadingUsed: Int（本月专业解读已用次数）
  - monthlyResetDate: Date（本月配额重置时间）
  - lastSyncAt: Date
```

**同步策略**：
1. App 启动时拉取 CloudKit，与本地合并取较大值（防覆盖）
2. 每次消费/购买后立即更新本地 + 异步写 CloudKit
3. iCloud 不可用时仅用本地，不阻塞正常使用
4. 购买收据 StoreKit 2 本地校验，CloudKit 仅同步余额数字

**开发工作量**：约 2–3 天

## 五、大师点券余额展示位置

**结论：「我的」页面 + 摇卦结果页解读模式选择处，双点位展示。**

### 5.1 「我的」页面（图二）— 新增余额显示

**当前状态**：只显示「今日剩余 X 次」（专业解读次数）。  
**新增内容**：在身份卡片下方或「今日剩余」区域旁，增加点券余额区域。

**展示规则**：
- 有点券余额时：显示「大师解读剩余 X 次」和「推演剩余 X 次」
- 两个余额均为 0 时：隐藏该区域，不占用空间
- 会员用户的赠送次数单独标注「赠 1次」（与点券余额区分）

**UI 位置**：`今日剩余` 卡片的副文本区，或其右侧小标签（不新增大块区域，避免页面臃肿）。

**参考文案**：
```
今日剩余   大师 ×3 · 推演 ×1
  1次      点击起卦后可用
```

### 5.2 摇卦结果页 / 解读模式选择区域 — 新增余额提示

**当前状态**：用户在结果页看到「大师深度解读」按钮时，不知道自己有没有余额。  
**新增内容**：在大师解读按钮旁或下方，显示当前可用次数。

**展示规则**：
- 有大师余额（含赠送）：按钮显示「大师深度解读（剩余 X 次）」
- 余额为 0：按钮显示「大师深度解读 ¥12」，点击弹出 MasterReadingCheckoutView
- 会员赠送次数：同样计入显示（赠送和点券合并显示剩余总量）

## 六、次数限制拦截提示设计

每种次数耗尽的场景，都需要对应的引导提示，**不能只显示「次数不足」的错误，要直接给出解决路径**。

### 6.1 追问达到 66次上限

**触发**：免费用户第3轮 / 付费用户第66次追问发送后

**免费用户（第3轮到达）**：
- 位置：第3次 AI 回复末尾，inline 卡片（非弹框）
- 样式：金色渐变边框圆角卡片，嵌入聊天流
- 文案：
  ```
  ✨ 本次卦象还有更多维度可以深聊
  开通会员，每月 66次专业追问 →
  ```
- 行动：点击跳转 ProUpgradeView

**付费用户（第66次到达）**：
- 位置：第66次 AI 回复末尾，inline 提示条
- 文案：「本卦追问已达上限（66次）。如需继续探索，建议重新起卦」
- 无按钮，仅提示，不跳转

---

### 6.2 专业解读月度配额用完

**触发**：月会员用完 66次/月 或 年会员用完 88次/月，再次起卦时

**UI 形式**：问题页底部弹出半屏 Sheet（可关闭，不强制）

### 6.6 大师模式「重新推演」次数限制

**适用场景**：用户在大师解读结果页点击「重新起卦/重新推演」

**UI 提示**（弹出 Alert 或 Toast）：

本次重新生成后，原有解读将被覆盖。
确认重新生成？

## 十、iCloud/CloudKit 同步实现规范

### 10.1 CloudKit 数据模型

```swift
struct UserQuotaRecord {
    static let recordType = "UserQuota"
    
    var masterCredits: Int       // 大师点券余额（购买所得）
    var deductionCredits: Int    // 推演点券余额（购买所得）
    var monthlyMasterGiftUsed: Int  // 本月大师赠送已用次数
    var monthlyReadingUsed: Int  // 本月专业解读已用次数
    var monthlyResetDate: Date   // 本月配额重置时间
    var lastUpdatedAt: Date
}
```

### 10.2 同步时机

| 事件 | 操作 |
|-----|------|
| App 启动 | 从 CloudKit 拉取，与本地合并（余额取较大值） |
| 购买点券成功 | 立即更新本地 + 异步写 CloudKit |
| 消费大师/推演点券 | 立即更新本地 + 异步写 CloudKit |
| 使用大师赠送次数 | monthlyMasterGiftUsed +1，写 CloudKit |
| 专业解读完成 | monthlyReadingUsed +1，写 CloudKit |
| 检测到新月份 | 重置 monthlyReadingUsed = 0，monthlyMasterGiftUsed = 0 |

### 10.3 降级策略

- iCloud 不可用：仅用本地，正常使用不受阻
- 新设备无 CloudKit 记录：从 0 开始，不伪造余额
- 购买校验：StoreKit 2 本地校验，CloudKit 只同步数字

## 十四、历史记录存档规则

历史列表里的一条，是**一次起卦的一次解读**。不按问题文字合并。问题和卦象写在这条上，推演和追问都挂在这条下面，不单独再开历史。

### 14.1 什么算同一条

| 用户做了什么 | 历史里怎么记 |
|---|---|
| 同一解卦结果页第一次保存 | 新建一条：问题、卦象、这次解读 |
| 同一页再点「保存」，没有重新解读 | 不再新建，提示已在历史中 |
| 点「重解」生成新解读后再保存 | 再新建一条。旧的那条，包括上面的推演和追问，原样留下 |
| 同一个问题重新摇卦 | 也是新的一条。问题文字相同，起卦不同 |

一个问题可以对应多条历史。区分标准是哪一次起卦、哪一次解读，不是问题这句话。

### 14.2 解卦结果：同一页只保存一次

解卦结果页的「保存」只负责这一次解读。

- 第一次保存：写入问题、卦象、解读，生成一条历史。
- 同一页再次保存：不更新、不新增。
- 重解之后再保存：按新的一次解读另存一条，旧记录保留。

### 14.3 推演：挂在当前这条上，多次推演只留最新一次

「保存推演」不单独开历史，只给当前这条解卦结果补上或换上推演。只在用户点击「保存推演」时写入，生成成功后不自动落库。

- 这条解卦还没进历史：点「保存推演」时，把问题、卦象、解读和这次推演一起写成一条。
- 这条解卦已经在历史里：不再新建解卦记录，只把推演写到这一条上。
- 同一解卦结果页推了好几次：历史里只留最后一次。已有推演时，保存前确认：「已有推演，保存将替换为本次结果。」确认后才替换；取消则保留旧推演，本次结果只留在当前页。
- 保存推演不动这条上的追问。

### 14.4 追问：自动保存，跟着对应的解卦结果走

追问没有单独的保存按钮。用户发出追问并得到回复后，自动写入历史，挂在对应的那一条解卦结果上。

- 这条解卦还没进历史：第一次成功追问时，自动把问题、卦象、解读写成一条，再把追问挂上去。
- 这条解卦已经在历史里：不新建解卦记录，追问追加进这一条已有的会话。
- 同一解卦结果页只有一条追问会话。之后的消息继续追加，不按每条消息另开历史。
- 只打开追问、没有成功发出，或回复失败：不写入历史。
- 重解后的新解读页，追问算新的一条；旧追问留在旧记录上。
- 自动保存追问不改动这条上的推演。

### 14.5 三条放在一起

| | 解卦结果 | 推演 | 追问 |
|---|---|---|---|
| 何时写入 | 用户点「保存」 | 用户点「保存推演」 | 追问成功后自动写入 |
| 还没进历史时 | 新建一条 | 连同问题、卦象、解读一起新建一条 | 连同问题、卦象、解读一起新建一条 |
| 已经在历史里 | 同一页不再保存 | 只更新这一条上的推演 | 追加到这一条的追问会话 |
| 同一页做了多次 | 只保留这一次解读 | 只留最新一次，覆盖前确认 | 同一条会话里追加 |
| 重解后再操作 | 另存一条新历史 | 挂到新的那条上 | 挂到新的那条上 |
